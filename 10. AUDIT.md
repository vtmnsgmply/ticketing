# Audit Module

## Objective

Build the system-wide Audit Log module for the Ticketing System.

Before making any changes:

1. Read `1. AGENTS.md`.
2. Review the completed implementation from:
   - `2. LOGIN.md`
   - `3. TICKET.md`
   - `4. ADMIN.md`
   - `5. CUSTOMER-DASHBOARD.md`
   - `6. STAFF-DASHBOARD.md`
   - `7. MANAGER-DASHBOARD.md`
   - `8. NOTIFICATION.md`
   - `9. REPORTING.md`
3. Inspect the existing `frontend` and `backend` code before modifying anything.
4. Preserve the existing authentication, authorization, ticket workflows, dashboards, notifications, reporting logic, database structure, API conventions, and UI conventions.
5. Reuse existing Requests, Services, Repositories, models/entities, middleware, events, utilities, and audit-related code wherever appropriate.
6. Do not duplicate working functionality.
7. Follow the required backend architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

Audit logging may also be triggered internally by business operations:

```text
Business Action
    ↓
Service
    ↓
AuditLogService
    ↓
AuditLogRepository
    ↓
MySQL
```

Controllers must remain thin.

Validation belongs in the Request layer.

Business logic belongs in the Service layer.

Database access belongs in the Repository layer.

# Audit Log vs Ticket Activity

The system already has operational ticket activity.

Keep the two concepts separate.

## Ticket Activity

Used for ticket-specific operational history:

```text
Ticket created
Ticket assigned
Ticket reassigned
Status changed
Priority changed
Customer replied
Agent replied
Internal note added
Ticket resolved
Ticket reopened
```

Stored in:

```text
ticket_activities
```

Ticket activity may be visible to authorized Staff, Managers, and Administrators.

---

## Audit Log

Used for system-wide administrative, security, and privileged actions.

Stored in:

```text
audit_logs
```

Examples:

```text
User created
User disabled
User role changed
Department created
SLA changed
System settings changed
Email settings changed
Administrator override performed
Login failure threshold reached
Sensitive configuration changed
```

Do not replace `ticket_activities` with `audit_logs`.

Do not unnecessarily duplicate every ordinary ticket event into the audit table.

Audit records should be treated as append-only application records.


# Security Requirements

- Audit endpoints require authentication.
- Global audit access is Administrator-only by default.
- Never expose passwords.
- Never expose password hashes.
- Never expose tokens.
- Never expose SMTP passwords.
- Never expose API keys.
- Never expose database credentials.
- Sanitize old/new values before persistence.
- Prevent stored XSS in displayed metadata.
- Prevent SQL injection in filters.
- Whitelist sortable columns.
- Prevent IDOR.
- Protect export endpoints.
- Rate limit expensive export/search endpoints where appropriate.
- Do not let users modify audit records through normal application APIs.
- Do not expose stack traces.
- Use CSRF protection where applicable.
- Use secure authenticated API requests.

# Do Not

Do not:

- Replace existing authentication.
- Replace the backend framework.
- Replace ticket_activities with audit_logs.
- Create a duplicate audit table.
- Log passwords.
- Log password hashes.
- Log tokens.
- Log SMTP passwords.
- Log API secrets.
- Log entire HTTP request bodies.
- Log entire HTTP response bodies.
- Allow ordinary users to edit/delete audit records.
- Give Managers global audit access by default.
- Put audit business logic in Controllers.
- Put raw SQL in Services.
- Put business logic in Repositories.
- Store huge payloads unnecessarily.
- Build SIEM integrations in this phase.
- Build AI anomaly detection.
- Rewrite unrelated working code.
