# Admin Module

## Objective

Build the Administration module for the Ticketing System.

Before making any changes:

1. Read the repository's `AGENTS.md`.
2. Inspect the existing `frontend` and `backend` directories.
3. Preserve the existing framework, dependencies, authentication, authorization, ticket module, and database structure.
4. Reuse the roles, users, departments, categories, priorities, SLA rules, system settings, notifications, and audit log tables already implemented.
5. Do not replace working authentication or ticket logic.
6. Follow the required backend architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

Controllers must remain thin.

Validation belongs in the Request layer.

Business logic belongs in the Service layer.

Database access belongs in the Repository layer.

---

# Scope

Implement the Administration module with the following capabilities:

```text
Admin Dashboard
User Management
Role Management
Department Management
Category Management
Priority Management
SLA Management
Email Settings
System Settings
Audit Log Viewer
```

This phase must focus on administrative configuration and management.

Do not build advanced reporting, SMS, WhatsApp, Messenger, Telegram, AI, billing, or third-party integrations in this phase.

# Administrator Access

Only authorized Administrator users may access the full Administration module.

Managers may receive limited access only where explicitly permitted.

Staff / Agents and Customers must not have access to administrative configuration.

Backend authorization is mandatory.

Do not rely only on hiding admin navigation items in React.

# Administrator Safety Rule

Prevent accidental removal or disabling of the final active Administrator account.

Recommended rule:

```text
The system must always retain at least one active Administrator.
```

If an action would leave zero active administrators, reject it with a business-rule error.

Example:

```json
{
  "success": false,
  "message": "At least one active Administrator account must remain."
}
```

# Existing Ticket SLA Rule

Changing an SLA rule should not silently rewrite historical SLA deadlines for existing tickets unless explicitly requested.

Recommended default behavior:

```text

```

If future scope requires SLA recalculation for existing tickets, implement it as a separate explicit administrative action.
