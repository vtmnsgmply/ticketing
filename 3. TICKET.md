# Ticket Module

## Objective

Build the core Ticket Management module for the Ticketing System.

Before making any changes:

1. Read the repository's `AGENTS.md`.
2. Inspect the existing `frontend` and `backend` directories.
3. Preserve the existing framework, dependencies, conventions, and authentication implementation.
4. Reuse the authentication and role system already implemented in `login.md`.
5. Do not replace working authentication, authorization, routing, or database configuration.
6. Follow the required backend architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

Controllers must remain thin.

Validation belongs in the Request layer.

Business logic belongs in the Service layer.

Database access belongs in the Repository layer.

---

# Scope

Implement the core ticket lifecycle.

The module must support:

- Create ticket
- View ticket
- View ticket list
- Update ticket details where permitted
- Assign ticket
- Reassign ticket
- Change ticket status
- Change ticket priority
- Add customer reply
- Add staff / agent reply
- Add internal note
- Upload attachments
- View attachments
- View activity timeline
- Search tickets
- Filter tickets
- Pagination
- SLA deadline initialization
- First-response tracking
- Resolution tracking
- Reopen ticket where permitted
- Close ticket
- Cancel ticket where permitted
- Role-based ticket permissions
- Web notification hooks where appropriate
- Email notification hooks where appropriate

Do not build advanced management reporting in this phase unless required to support ticket operations.

Do not build SMS, WhatsApp, Messenger, Telegram, AI, or third-party ticket integrations in this phase.

# Reopen Logic

Customers may reopen tickets only if permitted.

Recommended initial business rule:

- `Resolved` tickets may be reopened.
- `Closed` tickets may not be reopened by customers unless explicitly configured.
- `Cancelled` tickets may not be reopened by customers.
- Managers/Admins may have broader permissions.

When reopened:

```text
status = Open
resolved_at = null
```

Record the event in `ticket_activities`.

Do not erase previous resolution activity.

# Customer Permissions

Customers may:

- Create tickets.
- View their own tickets.
- View allowed messages on their own tickets.
- Reply to their own tickets.
- Upload attachments to their own tickets.
- View status and SLA-related information intended for customers.
- Reopen eligible resolved tickets.
- Update limited ticket information if explicitly allowed.

Customers may not:

- View another customer's ticket.
- View internal notes.
- Assign agents.
- Reassign tickets.
- Change departments unless explicitly allowed.
- Access management data.
- Change internal SLA configuration.
- Access audit-only information.
- Close/cancel tickets unless the business rule explicitly permits it.

---

# Agent / Staff Permissions

Agents may:

- View tickets within permitted departments/scope.
- View tickets assigned to them.
- Reply to customers.
- Add internal notes.
- Change allowed statuses.
- Change priority when permitted.
- Upload attachments.
- View ticket activity.
- Work assigned tickets.

Assignment permissions should be configurable by role/business rule.

---

# Manager Permissions

Managers may:

- Perform Agent actions.
- View department/team tickets.
- Assign tickets.
- Reassign tickets.
- View unassigned tickets.
- Change priorities.
- Change statuses.
- Resolve tickets.
- Close tickets where permitted.
- View operational ticket data.

---

# Administrator Permissions

Administrators may:

- Access all tickets.
- Assign/reassign tickets.
- Change ticket status and priority.
- View all internal notes.
- View all ticket activity.
- Perform administrative ticket actions.
- Override certain restrictions where appropriate.

Administrative overrides must still be logged.
