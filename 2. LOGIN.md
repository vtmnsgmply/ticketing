# Login and Authentication Module

## Objective

Build the authentication and authorization foundation for the Ticketing System.

Before making changes, read the repository's `AGENTS.md` and inspect the existing `frontend` and `backend` directories.

Do not replace the existing backend framework or frontend setup.

The implementation must follow the project's required architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

---

# Scope

Implement the following authentication features:

- Login
- Logout
- Authenticated user session/token handling
- Current authenticated user endpoint
- Role-based access control
- Protected backend routes
- Protected frontend routes
- Unauthorized access handling
- Disabled account handling
- Secure password handling
- Initial administrator setup
- Authentication-related validation
- React login interface
- SweetAlert2 success/error handling

Do not build the full ticketing module yet.

---

# Supported Roles

The system must support the following roles:

```text
Customer
Staff / Agent
Manager
Administrator
```

Each authenticated user must have a valid role.

Backend authorization must enforce access rules.

Frontend route protection alone is not sufficient.

# Database Rules

- Use migrations or the backend framework's equivalent schema-management feature.
- Use proper foreign keys where appropriate.
- Add a unique index to the user email field.
- Store passwords using the backend framework's secure password hashing mechanism.
- Never store plain-text passwords.
- Never hardcode production database credentials.
- Do not expose password hashes through API responses.
- Use environment variables for database configuration.

---

# Initial Administrator

Provide a safe way to create the initial Administrator account.

Preferred options:

- Seeder
- CLI command
- Framework-supported setup process

Do not hardcode a real production password in source code.

Suggested `.env.example` variables:

```env
ADMIN_NAME=System Administrator
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=
```

Do not commit a real administrator password.

# Backend Architecture

## Request Layer

Create the appropriate Request classes for authentication.

Examples:

```text
LoginRequest
RegisterRequest
UpdateProfileRequest
ChangePasswordRequest
ForgotPasswordRequest
ResetPasswordRequest
```

Only create requests required by the current implementation.

The Request layer is responsible for:

- Required field validation
- Email validation
- Password validation
- Input normalization
- Validation error responses

The Request layer must not:

- Query MySQL directly
- Authenticate users directly
- Contain application business logic

---

# Service Layer

Create an authentication service.

Example:

```text
AuthService
```

Responsibilities may include:

- Authenticating credentials
- Checking whether the user account is active
- Generating or managing authentication tokens/sessions
- Updating `last_login_at`
- Logging users out
- Returning authenticated user information
- Performing authentication-related business rules

The Service must use repositories for database access.

Do not write raw database queries directly inside the Service.

---

# Repository Layer

Create the required authentication/user repository.

Example:

```text
UserRepository
RoleRepository
```

Responsibilities include:

- Find user by email
- Find user by ID
- Read user role
- Update last login time
- Persist authentication-related user changes
- Query users where required

Business logic must not be placed inside repositories.

---

# Controller

Controllers must remain thin.

Example authentication controller methods:

```text
login()
logout()
me()
```

The controller should:

1. Receive the validated request.
2. Call the appropriate Service.
3. Return the standardized API response.

Do not place authentication business logic directly in the controller.

# Login Validation

At minimum validate:

## Email

- Required
- Valid email format

## Password

- Required
- Must not be empty

Do not reveal whether a specific email address exists when authentication fails.

Use a generic authentication failure message such as:

```text
Invalid email or password.
```

---

# Disabled Accounts

The `users` table should support an active/disabled state.

Example:

```text
is_active
```

If a disabled user attempts to log in:

- Do not authenticate the user.
- Return an appropriate error response.
- Do not expose unnecessary internal account information.

Example message:

```text
Your account is currently unavailable. Please contact the administrator.
```

# API Response Format

Use consistent JSON responses.

## Login Success

Example:

```json
{
  "success": true,
  "message": "Login successful.",
  "data": {
    "user": {
      "id": 1,
      "name": "System Administrator",
      "email": "admin@example.com",
      "role": "administrator"
    }
  }
}
```

If token-based authentication is used, include the token only as appropriate for the selected authentication strategy.

## Login Failure

Example:

```json
{
  "success": false,
  "message": "Invalid email or password."
}
```

## Validation Failure

Example:

```json
{
  "success": false,
  "message": "Validation failed.",
  "errors": {
    "email": [
      "The email field is required."
    ]
  }
}
```

## Unauthorized

Example:

```json
{
  "success": false,
  "message": "Unauthorized."
}
```

Use appropriate HTTP status codes.

Unauthenticated users attempting to access protected pages should be redirected to:

```text

```

Authenticated users should not normally be sent back to the login page unless they log out or their session expires.

# Backend Authorization

Backend authorization is mandatory.

Never rely only on frontend route hiding.

Protected backend endpoints must validate:

1. The user is authenticated.
2. The user account is active.
3. The user's role is permitted to access the resource/action.

Future examples:

```text
Customer:
- Own tickets only

Agent:
- Permitted department tickets

Manager:
- Department/team tickets and reports

Administrator:
- Full administrative access
```

# Security Requirements

Implement basic authentication security.

Requirements:

- Password hashing
- Secure authentication mechanism
- Backend authorization
- Login validation
- Protection against unauthorized API access
- Do not expose password hashes
- Do not expose database credentials
- Do not expose stack traces to the frontend
- Use environment variables for secrets
- Use HTTPS in production
- Validate all incoming authentication data

Where supported by the backend framework, use built-in protections for:

- CSRF
- Session security
- Rate limiting
- Brute-force login protection

# Logout

Logout must:

1. Invalidate the current authenticated session/token as appropriate.
2. Clear frontend authentication state.
3. Redirect the user to `/login`.

Do not simply remove frontend state while leaving a server-side session/token valid.

# Current User Endpoint

Implement:

```text
GET /api/me
```

It should return the current authenticated user's safe profile information.

Example:

```json
{
  "success": true,
  "data": {
    "id": 1,
    "name": "System Administrator",
    "email": "admin@example.com",
    "phone": null,
    "company": null,
    "role": {
      "id": 4,
      "name": "Administrator",
      "slug": "administrator"
    }
  }
}
```

Never return:

- Password
- Password hash
- Authentication secrets
- Sensitive internal fields

---

# Session Persistence

On frontend refresh, the application should determine whether the user is still authenticated.

Recommended flow:

```text
React App Loads
    ↓
Authentication State Initializes
    ↓
GET /api/me
    ↓
Valid Session?
   /       \
 Yes       No
 ↓          ↓
Restore    Remain
User       Logged Out
```

Show a loading state while authentication is being determined to prevent incorrect route flashes.
