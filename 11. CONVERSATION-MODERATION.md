# Conversation Profanity & Moderation Filter

## Purpose

Implement an enterprise-ready profanity and prohibited-language moderation layer for the ticket conversation system.

The feature must protect customer/staff conversations from offensive or prohibited language without breaking the existing ticket workflow, RBAC, audit rules, notifications, or message history.

**All enforcement must occur on the Laravel backend before conversation content is persisted or distributed through notifications.**

---

# 1. Primary Behavior

The moderation system must support four modes:

```text
MASK
BLOCK
FLAG
MASK + FLAG
```

Recommended default:

```text
MASK + FLAG
```

### MASK
Allow the message to be sent, but replace prohibited words with masked text.

Example:

```text
Input:
This service is fucking terrible.

Displayed:
This service is f*****g terrible.
```

### BLOCK
Reject the message with a validation-style response:

```text
Your message contains language that is not permitted.
Please revise the message before sending.
```

### FLAG
Allow the message to continue normally but record the moderation event for manager/admin review.

Do not permanently hard-code moderation behavior inside controllers.

# 5. Original Message Handling

The normal:

```text
ticket_messages.message
```

field must contain the safe/filtered version.

If retaining the original content is required:

- Store it only when a violation occurs.
- Encrypt it.
- Never return it from standard ticket APIs.
- Never include it in normal notifications.
- Never expose it to customers.
- Never write it to Laravel logs.
- Restrict access to explicitly authorized moderation reviewers.

If original-content retention is not required, do not store it.

---

# 6. Matching Rules

Do not use naive substring matching.

Incorrect:

```php
str_contains($message, 'ass');
```

This can incorrectly censor:

```text
class
assignment
pass
assistant
```

Use token-aware or word-boundary-aware matching where appropriate.

Conceptual regex:

```regex
\bWORD\b
```

Always escape administrator-provided values before constructing regex:

```php
preg_quote($word, '/')
```

Matching should be case-insensitive.

---

# 7. Normalization

Create an isolated normalization stage.

Recommended normalization:

```text
lowercase conversion
Unicode normalization
trim repeated whitespace
controlled replacement of common substitutions
```

Potential substitution map:

```text
@ → a
4 → a
3 → e
1 → i
! → i
0 → o
5 → s
$ → s
```

This can help detect:

```text
sh1t
f@ck
```

Be conservative. Aggressive normalization can create false positives.

---

# 8. Obfuscation

Version 1 should reasonably detect common forms such as:

```text
f*ck
f@ck
sh1t
s h i t
f.u.c.k
```

Recommended strategy:

1. Preserve original text temporarily in memory.
2. Generate a normalized comparison representation.
3. Detect prohibited terms against the normalized representation.
4. Map the match back to the original text when masking.

If character mapping becomes unreliable, prefer safe blocking/flagging rather than corrupting innocent text.

---

# 9. Masking Rules

Default masking behavior:

```text
fuck    → f**k
fucking → f*****g
shit    → s**t
```

Recommended rule:

```text
preserve first and last character
replace internal characters with *
```

For terms shorter than three characters, mask the full term.

Do not modify non-matching text.


```text

```

# 17. RBAC

### Customer

```text
Can submit moderated messages
Cannot manage blocked terms
Cannot view moderation events
Cannot view original content
```

### Staff / Agent

```text
Can submit moderated replies/internal notes
Cannot manage global moderation rules
Cannot view encrypted original content by default
```

### Manager

```text
Can review flagged events only within permitted ticket/department scope
Cannot modify global blocked-term settings unless granted
```

### Administrator

```text
Can manage moderation settings
Can manage blocked terms
Can review all moderation events
Can perform escalation actions
```

All authorization must be enforced on the backend.

# 18. Department Scope / IDOR

If a manager cannot open a ticket, that manager must not be able to open its moderation event.

Example:

```text
No access to TKT-12345
=
No access to moderation event for TKT-12345
```

Prevent IDOR.


# 26. XSS Safety

Profanity filtering is not HTML sanitization.

Continue escaping user-generated conversation content in React.

Avoid:

```jsx
dangerouslySetInnerHTML
```

unless the project already has a safe sanitization strategy.

# 28. False Positives

Avoid censoring legitimate words such as:

```text
class
assignment
pass
assistant
```

Every moderation rule should be independently enableable/disableable.

Admins must be able to disable a problematic rule without deploying new code.

---

# 29. Seed Data

Do not ship a huge unreviewed profanity dictionary.

If seed data is included:

- Keep it small.
- Make every rule editable.
- Make every rule disableable.
- Avoid unnecessary sensitive/slur content in demo screenshots.
- Clearly mark it as initial configuration.

The production administrator owns the final moderation policy.

# 32. Performance

Do not query the database once per blocked word.

Bad:

```text
message
→ query word A
→ query word B
→ query word C
```

Preferred:

```text
load active rules once
→ cache
→ process message in memory
```

Avoid pathological regex behavior.

Moderation must not introduce duplicate API requests or notifications.

---

# 33. Transaction Behavior

For `MASK + FLAG`, the filtered message and moderation event should remain logically consistent.

Recommended principles:

- Never allow unsafe original content because moderation-event logging failed.
- Prefer transactional consistency where practical.
- Notification failure must not roll back a valid saved ticket message.
- Moderation failure should fail safe.

# 42. Implementation Constraints

Do not:

- Rewrite the ticket module solely for moderation.
- Implement moderation only in React.
- Hard-code the blocked list inside controllers.
- Send raw prohibited content to Telegram or Email.
- Log raw/original content in debug logs.
- Permanently delete moderation history by default.
- Break RBAC.
- Break ticket scope rules.
- Break notification failure isolation.
- Add fake moderation metrics.
- Add artificial delays.
- Remove React StrictMode.
- Change unrelated business logic.
