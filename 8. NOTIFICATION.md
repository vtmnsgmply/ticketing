# Notification Module

## Objective

Build the Notification module for the Ticketing System.

Before making any changes:

1. Read `1. AGENTS.md`.
2. Review the completed implementation from:
   - `2. LOGIN.md`
   - `3. TICKET.md`
   - `4. ADMIN.md`
   - `5. CUSTOMER-DASHBOARD.md`
   - `6. STAFF-DASHBOARD.md`
   - `7. MANAGER-DASHBOARD.md`
3. Inspect the existing `frontend` and `backend` code before modifying anything.
4. Preserve the existing authentication, authorization, ticket workflows, customer portal, staff portal, manager portal, admin module, database structure, and API conventions.
5. Reuse existing Services, Repositories, Requests, models/entities, routes, components, events, queues, and utilities wherever appropriate.
6. Do not duplicate working functionality.
7. Follow the required backend architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

Notification creation may also be triggered internally by application events:

```text
Business Event
    ↓
Service
    ↓
Notification Service
    ↓
Notification Repository
    ↓
MySQL
    ↓
Web / Email Delivery
```

Controllers must remain thin.

Validation belongs in the Request layer.

Business logic belongs in the Service layer.

Database access belongs in the Repository layer.

# Ticket Created Notification

When a Customer creates a ticket:

Customer should receive:

```text
Web notification
Email confirmation if enabled
```

Potential message:

```text
Your ticket TKT-10023 has been created successfully.
```

Relevant Staff/Manager recipients may receive:

```text
New ticket created
```

depending on department routing and notification rules.

Do not notify every Staff member in the entire system if the ticket belongs to one department.

---

# Ticket Assigned Notification

When a ticket is assigned:

The assigned Agent should receive:

```text
Web notification
Email notification if enabled
```

Example:

```text
Ticket TKT-10023 has been assigned to you.
```

The Customer does not need to receive an assignment notification unless explicitly configured.

---

# Ticket Reassigned Notification

When reassigned:

Notify:

```text
New assigned Agent
Previous Agent where appropriate
Manager where appropriate
```

Example:

```text
Ticket TKT-10023 has been reassigned to you.
```

Do not reveal unnecessary internal staff information to the Customer.

---

# Customer Reply Notification

When a Customer replies:

Notify:

```text
Assigned Agent
Relevant Manager if needed
```

If the ticket is unassigned, notify the appropriate department queue or Manager according to system rules.

Example:

```text
Customer replied to ticket TKT-10023.
```

---

# Agent Reply Notification

When an Agent replies:

Notify the Customer:

```text
Web notification
Email notification if enabled
```

Example:

```text
Support replied to ticket TKT-10023.
```

Do not expose internal note content.

---

# Internal Note Notification

Internal notes must never generate Customer notifications.

Internal note notifications may be sent to:

```text
Assigned Agent
Manager
Other Staff explicitly mentioned/targeted
```

only if the existing business rules require it.

Default behavior:

```text
Do not send broad notifications for every internal note.
```

---

# Ticket Resolved Notification

When a ticket is resolved:

Notify Customer:


Potential message:

```text

```



# SLA Due Soon Notification

Create operational notifications for tickets approaching SLA breach.

Recommended recipients:

```text
Assigned Agent
Relevant Manager
```

Optional:

```text
Department Manager
```

Do not notify Customers about internal SLA due-soon events unless explicitly required.

---

# SLA Breach Notification

When an SLA is breached:

Notify:

```text
Assigned Agent
Relevant Manager
Administrator only if required
```

Example:

```text
Ticket TKT-10023 has exceeded its Resolution SLA.
```

If the ticket is unassigned, notify:

```text
Manager
Department queue owner
```

according to available system roles.

---

# SLA Notification Deduplication

Do not create repeated duplicate SLA notifications every time a monitoring job runs.

Example:

```text
sla_due_soon
sla_breached
```

should only be created once per relevant SLA event unless the business rule explicitly allows reminders.

Use metadata, status fields, or a notification lookup to prevent duplicates.

---

# Security Requirements

- Every notification endpoint requires authentication.
- Users can only access their own notifications.
- Users can only mark their own notifications as read.
- Notification links must still enforce ticket authorization.
- Never trust frontend recipient IDs for automated notifications.
- Never expose email credentials.
- Never expose internal notes to Customers.
- Never expose stack traces.
- Never expose mail provider secrets.
- Sanitize notification message content where user data is included.
- Prevent stored XSS.
- Validate notification preference input.
- Rate limit sensitive endpoints where appropriate.
- Protect Admin-only email test settings.
- Use CSRF protection where applicable.
- Use secure authenticated API requests.

---
