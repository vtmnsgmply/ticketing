# Reporting Module

## Objective

Build the Reporting module for the Ticketing System.

Before making any changes:

1. Read `1. AGENTS.md`.
2. Review the completed implementation from:
   - `2. LOGIN.md`
   - `3. TICKET.md`
   - `4. ADMIN.md`
   - `5. CUSTOMER-DASHBOARD.md`
   - `6. STAFF-DASHBOARD.md`
   - `7. MANAGER-DASHBOARD.md`
   - `8. NOTIFICATION.md`
3. Inspect the existing `frontend` and `backend` code before modifying anything.
4. Preserve the existing authentication, authorization, ticket workflows, dashboards, notification system, database structure, API conventions, and UI conventions.
5. Reuse existing Requests, Services, Repositories, models/entities, routes, components, filters, and utilities wherever appropriate.
6. Do not duplicate working functionality.
7. Follow the required backend architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Service
    ↓
Repository
    ↓
MySQL
```

Controllers must remain thin.

Validation belongs in the Request layer.

Business logic belongs in the Service layer.

Database access belongs in the Repository layer.

# First Response Time

Calculate First Response Time as:

```text
first_responded_at - created_at
```

for tickets with a valid customer-facing first response.

Internal notes do not count.

Tickets without a first response should not be included in average completed-response calculations unless the report explicitly shows pending response tickets.

---

# Average First Response Time

Recommended calculation:

```text
SUM(first_response_duration) / count(responded tickets)
```

Do not calculate average using tickets that have never received a first response unless clearly labeled.

---

# Resolution Time

Calculate ticket resolution time using:

```text
resolved_at - created_at
```

or the approved SLA calculation logic if waiting periods are excluded.

Use the same business rules throughout the system.

Do not implement conflicting resolution calculations between dashboard and reporting modules.

---

# Average Resolution Time

Use resolved tickets only.

Recommended:

```text
SUM(resolution_duration) / count(resolved tickets)
```

If reopened tickets are resolved multiple times, use the current approved reporting rule.

Recommended initial rule:

```text
Use the latest/current resolved_at value for current ticket-level reporting.
```

Do not invent historical resolution cycles unless ticket activity is explicitly used for advanced analysis.

---

# SLA Compliance

Define SLA compliance centrally.

Recommended ticket-level compliance:

```text

AND
Resolution SLA Met
```

```text
First Response SLA Compliance
Resolution SLA Compliance
Overall SLA Compliance
```

The latter is preferred for clarity.

---

# First Response SLA Compliance

Recommended calculation:

```text
Tickets responded before/equal first_response_due_at
-----------------------------------------------------
Tickets with required first response
```

Handle unresolved/unresponded tickets consistently.

---

# Resolution SLA Compliance

Recommended calculation:

```text
Tickets resolved before/equal resolution_due_at
------------------------------------------------
Resolved tickets with SLA targets
```

Also separately report active breached tickets.

# Database Query Performance

Reporting queries can become expensive.

Use:

```text
Indexes
Aggregations
Date-range filters
Pagination
Selective joins
```

Avoid loading all tickets into application memory and calculating reports in PHP/Node/Python unless the dataset is intentionally tiny.

Prefer database aggregation.


# Security Requirements

- Require authentication for all reporting endpoints.
- Enforce role-based reporting permissions.
- Enforce Manager department scope.
- Enforce Agent self-only reporting where applicable.
- Validate all filters.
- Whitelist sortable fields.
- Prevent SQL injection.
- Prevent IDOR.
- Do not expose sensitive personal data unnecessarily.
- Do not expose internal notes in aggregate/report exports unless explicitly required.
- Do not expose passwords or secrets.
- Do not expose stack traces.
- Use secure authenticated API requests.
- Use CSRF protection where applicable.
- Rate limit expensive report endpoints where appropriate.
