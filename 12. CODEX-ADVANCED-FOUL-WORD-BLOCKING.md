# Codex Instructions — Advanced Foul-Word Blocking & Obfuscation Detection

## Objective

Upgrade the existing `ConversationModerationService` so prohibited/foul language is blocked even when users intentionally disguise it using:

- accented letters
- Unicode variants
- mixed punctuation
- symbols
- leetspeak
- missing vowels
- repeated letters
- spaces between characters
- dots/dashes/underscores between characters
- zero-width/invisible characters
- visually similar Unicode characters
- mixed uppercase/lowercase
- common morphological variants
- deliberately malformed spellings

Examples that must be detected as the same prohibited family:

```text
fucking
fcking
fücking
fück!ng
f.u.c.k.i.n.g
f u c k i n g
f-u-c-k-i-n-g
f_u_c_k_i_n_g
fuccking
fuuucking
FÜCK!NG
f​u​c​k​i​n​g
```

The goal is **robust backend enforcement**, not merely exact-word matching.

Important: No profanity filter can mathematically guarantee detection of every possible adversarial encoding. Build a layered detection system that makes common and intentional obfuscation difficult while controlling false positives.

---

# 1. Enforcement Mode

For this implementation, prohibited foul language must be:

```text
BLOCKED
```

The message must not be persisted as a normal ticket reply when a prohibited match is confirmed.

API response example:

```json
{
  "success": false,
  "message": "Your message contains language that is not permitted. Please revise it and try again.",
  "errors": {
    "message": [
      "Prohibited language detected."
    ]
  }
}
```

Do not expose the detected blocked term to the user.

Do not reveal the matching algorithm.

Do not reveal which normalization rule triggered.

# 3. Use Multiple Representations of Every Message

Do not test only the raw input.

For every incoming message, generate several normalized representations.

Example:

```php
$forms = [
    'original'        => $original,
    'unicode'         => $unicodeNormalized,
    'ascii'           => $asciiFolded,
    'leet'            => $leetNormalized,
    'compact'         => $compact,
    'collapsed'       => $collapsedRepeats,
    'skeleton'        => $confusableSkeleton,
    'letters_only'    => $lettersOnly,
];
```

The detector should evaluate prohibited terms against multiple forms.

---

# 4. Stage 1 — Unicode Normalization

Use PHP's `intl` extension when available.

Preferred:

```php
Normalizer::normalize($text, Normalizer::FORM_KC);
```

or an equivalent safe normalization strategy.

Normalize compatibility variants so visually equivalent characters become easier to compare.

Do not assume all user input is ASCII.

Preserve the original message only in memory unless audit policy requires encrypted retention.

---

# 5. Stage 2 — Remove Combining Marks / Accents

Convert accented characters to their base form for comparison.

Examples:

```text
ü → u
ú → u
ù → u
û → u

á → a
à → a
ä → a
â → a

é → e
è → e
ë → e

í → i
ï → i

ó → o
ö → o
```

Therefore:

```text
fücking
```

must normalize toward:

```text
fucking
```

Use Unicode-aware processing.

Do not manually hard-code only the examples above. Implement general diacritic removal.

---

# 6. Stage 3 — Lowercase

Comparison forms should be case-insensitive.

Examples:

```text
FUCKING
Fucking
FuCkInG
FÜCK!NG
```

must resolve to the same normalized comparison family.

Use a Unicode-aware lowercase function such as:

```php
mb_strtolower()
```

---

# 7. Stage 4 — Remove Invisible Characters

Users may insert invisible characters to bypass filters.

Strip or normalize:

```text
zero-width space
zero-width non-joiner
zero-width joiner
word joiner
byte-order mark
soft hyphen
other common format/control characters
```

Examples:

```text
f​u​c​k
```

must be detected the same as:

```text
fuck
```

Do this before word matching.

Do not remove ordinary printable Unicode indiscriminately.

---

# 8. Stage 5 — Normalize Common Leetspeak

Create a controlled substitution map.

Example:

```text
0 → o
1 → i
! → i
3 → e
4 → a
@ → a
5 → s
$ → s
7 → t
+ → t
```

Potential examples:

```text
sh1t
f@ck
b1tch
```

must be normalized before comparison.

Keep this map configurable in code/config rather than scattering replacements across controllers.

---

# 9. Stage 6 — Normalize Visual Homoglyphs

Users may substitute visually similar Unicode letters.

Examples can include characters from:

```text
Cyrillic
Greek
full-width Latin
mathematical alphanumerics
other Unicode look-alikes
```

Create a conservative confusable-character skeleton.

Example concept:

```text
Latin a
Cyrillic а
full-width ａ
```

should map to a canonical comparison representation when safe.

Do not create an uncontrolled global character-conversion table that damages legitimate multilingual text.

Apply confusable normalization for moderation comparison only.

Never rewrite the user's actual displayed content based on this normalization.

---

# 10. Stage 7 — Separator Removal

Users may insert separators between letters.

Build a comparison representation that removes separators between alphabetic characters.

Examples:

```text
f.u.c.k
f-u-c-k
f_u_c_k
f u c k
f/u/c/k
```

should produce a comparison form similar to:

```text
fuck
```

Do not simply remove all punctuation from the entire message and use only substring matching.

Keep both:

```text
token-preserving form
compact comparison form
```

to reduce false positives.

---

# 11. Stage 8 — Repeated Character Collapse

Users may intentionally repeat letters:

```text
fuuuck
fuuuuuck
fuccck
fuucckk
```

Build another comparison form where excessive repetitions are collapsed.

Example:

```text
fuuuuuck
```

can produce:

```text
fuck
```

or:

```text
fuuck
```

depending on configured collapse rules.

Recommended:

```text
3+ repeated identical characters → 1 or 2 comparison characters
```

Keep the raw form as another detection input.

Do not alter the actual persisted user content for an allowed message.

---

# 12. Stage 9 — Missing-Vowel / Compressed Variants

The system must detect common intentional contractions such as:

```text
fck
fcking
```

Exact string matching alone cannot catch this.

Create a canonical blocked-term family strategy.

For each blocked term, optionally store/generate:

```text
canonical form
vowel-reduced form
common suffix forms
known aliases
```

Example conceptual representations:

```text
fucking
fcking
fck
```

Do not apply unrestricted vowel deletion to every word in the English language without safeguards; this can create severe false positives.

Only use compressed-form matching for blocked terms that have explicitly generated or approved compressed variants.

Upgrade blocked-term storage so one prohibited concept can have multiple approved detection forms.

```text

```

---

# 14. Morphological Variants

A blocked root may appear in multiple grammatical forms.

Example concept:

```text
base
plural
past tense
-ing form
-er form
-ed form
```

Do not simply use unrestricted substring matching.

Preferred strategies:

1. Explicit variants for high-risk terms.
2. Carefully bounded suffix rules.
3. Stem/root logic only when it is tested against false positives.

If using a root rule, require safe token boundaries or a high-confidence normalized token.

---

# 15. Layered Detection Order

Recommended order:

```text
Layer 1: exact token match
Layer 2: Unicode/diacritic normalized match
Layer 3: leetspeak normalized match
Layer 4: separator-compacted match
Layer 5: repeated-character collapsed match
Layer 6: approved variant match
Layer 7: conservative fuzzy match
```

A high-confidence match from any layer should block the message.

---

# 16. Fuzzy Matching

Use fuzzy matching only as a final layer.

Suitable approaches include:

```text
Levenshtein distance
Damerau-Levenshtein distance
similarity ratio
```

Do not fuzzy-match every message word against every blocked word without limits.

Performance and false-positive risks are too high.

Recommended constraints:

- Only fuzzy-check tokens within a reasonable length range.
- Only compare words with similar first/last character patterns when practical.
- Only allow very small edit distance.
- Use stricter thresholds for short words.
- Do not fuzzy-match blocked terms under 4 characters unless explicitly configured.
- Cache normalized blocked-term variants.

Example concept:

```text
blocked length 4–5: max distance 1
blocked length 6–9: max distance 1
blocked length 10+: max distance 2
```

These are starting rules only. Validate them with tests before production.

---

# 17. Never Use One Giant Regex

Do not generate a single giant regex containing the entire profanity dictionary and all obfuscation permutations.

Problems:

```text
performance
ReDoS risk
unmaintainable expressions
difficult debugging
false positives
memory usage
```

Build a predictable normalization + matching pipeline instead.

---

# 18. Regex Safety

Any database-provided term inserted into regex must be escaped:

```php
preg_quote($term, '/')
```

Avoid nested uncontrolled quantifiers.

Avoid patterns like:

```regex
.*.*.*
(a+)+
(.+)+
```

Test pathological long input.

---

# 19. False Positive Protection

The filter must not block normal words simply because they contain a prohibited sequence.

Examples that must be explicitly tested:

```text
class
assignment
pass
assistant
assessment
classic
Scunthorpe
```

Maintain:

```text
allowlist / exception rules
```

if production testing identifies legitimate false positives.

Recommended table:

```text
moderation_allowlist
```

or a configuration list if small.

Allowlist matching must also be normalized using the same Unicode pipeline.

---

# 20. Context-Aware Tokenization

Build both:

```text
token-level representation
compact-obfuscation representation
```

Use token boundaries for ordinary matching.

Use compact representations only for high-confidence obfuscation checks.

Example:

```text
"please pass the class"
```

must not be blocked because a prohibited substring happens to exist across legitimate words.

Do not concatenate the entire conversation into one letter stream and run unrestricted matching.

---

# 21. Mixed Character Detection

Detect words composed from mixed character classes.

Examples:

```text
fück!ng
f@c#k
FÜCK!NG
```

Recommended comparison steps:

```text
Unicode normalize
↓
remove combining marks
↓
lowercase
↓
confusable skeleton
↓
leet substitution
↓
remove internal separators
↓
compare
```

The original message must remain unchanged unless the message is allowed.

# 30. Internal Notes

Apply the same detection to internal staff notes.

```text

```

---

# 31. Performance Requirements

Do not perform:

```text
blocked_word_count × message_token_count × multiple DB queries
```

Required:

```text
Load active blocked terms + variants
↓
normalize once
↓
cache dictionary
↓
match in memory
```

Cache should be invalidated immediately when rules change.

Consider precomputing normalized forms when blocked-word rules are saved.

---

# 32. Long Message Protection

Set a reasonable maximum conversation length using the existing message validation policy.

Do not allow a user to submit multi-megabyte text that causes excessive normalization/fuzzy-matching CPU usage.

Fuzzy matching should have its own token-count and token-length limits.

---

# 33. Security — Fail Closed

If the moderation engine encounters an internal failure during a customer/staff message submission:

Preferred behavior:

```text
do not persist unmoderated content
return a safe temporary error
log only non-sensitive diagnostics
```

Example:

```text
We could not process your message safely. Please try again.
```

Do not silently bypass moderation when the moderation service throws an exception.

# 38. Detection Confidence

Internally classify matches:

```text
exact
normalized_exact
variant_exact
obfuscation_high_confidence
fuzzy
```

Recommended blocking:

```text
exact                    → BLOCK
normalized_exact         → BLOCK
variant_exact            → BLOCK
obfuscation_high_confidence → BLOCK
fuzzy                    → BLOCK only above conservative threshold
```

If fuzzy confidence is below threshold:

```text
ALLOW or FLAG
```

depending on configured policy.

Do not block low-confidence fuzzy matches by default.

```text
"detects configured prohibited terms and common intentional obfuscation patterns using layered normalization and matching."
```

This is technically accurate and defensible.

# 41. Codex Implementation Rules

Do not:

- Build a frontend-only filter.
- Rely on a single exact blacklist.
- Rely on one giant regex.
- Remove all punctuation globally and call it sufficient.
- Use unrestricted substring matching.
- Use unrestricted fuzzy matching.
- Hard-code all variants inside controllers.
- Log raw blocked messages.
- Send blocked content to Telegram or Email.
- Disable Unicode support.
- Break Filipino/non-English text.
- Break existing ticket message APIs.
- Break RBAC.
- Break manager department scope.
- Remove StrictMode.
- Add fake delays.
- Change unrelated modules.
