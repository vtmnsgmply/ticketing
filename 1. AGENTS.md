# Project Development Instructions

## Project Structure

This project is divided into two primary applications:

```text
/
├── frontend/
└── backend/
```

The frontend and backend must remain separated.

---

# Frontend

## ReactJS

The `frontend` directory will contain the ReactJS application.

Before making changes:

1. Inspect the `frontend` directory.
2. If ReactJS is already installed, preserve the existing project and dependencies.
3. If the directory is empty and ReactJS has not yet been initialized, initialize a React application using Vite.
4. Do not overwrite existing frontend files without first inspecting them.

Preferred setup:

```bash
cd frontend
npm create vite@latest . -- --template react
npm install
```

---

## SweetAlert

Install and use **SweetAlert2** for user-facing confirmation dialogs, alerts, success messages, warnings, and errors.

Install:

```bash
npm install sweetalert2
```

Import when required:

```javascript
import Swal from "sweetalert2";
```

Examples of where SweetAlert should be used:

* Successful form submissions
* Failed requests
* Delete confirmations
* Ticket closure confirmations
* Account disabling confirmations
* Important warnings
* Other actions requiring explicit user confirmation

Do not use browser-native:

```javascript
alert()
confirm()
prompt()
```

when SweetAlert2 can provide the same functionality.

---

# Backend

Before modifying the backend:

1. Inspect the existing backend project.
2. Determine the framework, language, dependencies, routing structure, ORM/database library, and existing conventions.
3. Preserve the existing backend framework.
4. Do not replace the backend technology stack unless explicitly requested.
5. Implement the architecture below using conventions appropriate to the existing backend framework.

---

# Backend Architecture

The backend must contain the following architectural layers:

```text
backend/
├── Request/
├── Services/
└── Repository/
```

If the backend framework requires these directories to live inside another directory such as `src`, `app`, or another application directory, follow the framework convention while preserving these architectural layers.

Example:

```text
backend/
└── app/
    ├── Request/
    ├── Services/
    └── Repository/
```

---

# Request Layer

The `Request` layer is responsible for handling and validating incoming request data.

Responsibilities include:

* Required field validation
* Data type validation
* Format validation
* Request sanitization where appropriate
* Normalization of incoming values
* Validation of IDs and references
* Validation of uploaded files
* Validation of authentication-related input
* Returning structured validation errors

Example responsibilities:

```text
CreateTicketRequest
UpdateTicketRequest
ReplyTicketRequest
AssignTicketRequest
ChangeTicketStatusRequest
LoginRequest
RegisterCustomerRequest
UpdateProfileRequest
```

The Request layer must **not**:

* Perform database queries directly
* Contain application business logic
* Implement ticket workflow rules
* Perform unrelated processing

---

# Service Layer

The `Services` layer contains the application's business logic.

Responsibilities include:

* Ticket workflow logic
* Ticket status transitions
* Ticket assignment
* Priority handling
* SLA calculation
* Ticket reopening logic
* Notification orchestration
* Permission/business-rule checks
* Activity logging orchestration
* Coordination between repositories
* Database transaction orchestration where needed

Examples:

```text
TicketService
UserService
DepartmentService
CategoryService
NotificationService
SLAService
ReportService
AuditLogService
```

The Service layer may call one or more repositories.

The Service layer must **not** contain raw SQL or directly communicate with MySQL.

---

# Repository Layer

The `Repository` layer is responsible for database communication and persistence.

Responsibilities include:

* Reading records
* Creating records
* Updating records
* Deleting records when permitted
* Database filtering
* Database searches
* Pagination queries
* Aggregate queries
* Reporting queries
* Relationships and persistence operations

Examples:

```text
TicketRepository
UserRepository
DepartmentRepository
CategoryRepository
NotificationRepository
AuditLogRepository
```

Only the Repository layer should directly communicate with the application's ORM/query builder/database access layer for normal application data operations.

Business rules must not be implemented inside repositories.

---

# Required Request Flow

All applicable backend requests must follow this architecture:

```text
User Request
    ↓
Route / Controller
    ↓
Request
    ↓
Validation
    ↓
Service
    ↓
Business Logic
    ↓
Repository
    ↓
MySQL Database
```

Responses return through:

```text
MySQL Database
    ↓
Repository
    ↓
Service
    ↓
Controller
    ↓
API Response
    ↓
Frontend
```

---

# Architecture Rules

The following rules are mandatory.

### Rule 1 — Controllers Must Stay Thin

Controllers should only:

* Receive validated requests
* Call the appropriate Service
* Return the appropriate HTTP/API response

Controllers must not contain substantial business logic.

---

### Rule 2 — Validation Belongs in Request

Incoming data must be validated before reaching business logic.

Do not perform significant request validation inside:

* Controllers
* Services
* Repositories

unless validation specifically depends on a business rule that belongs in the Service layer.

---

### Rule 3 — Business Logic Belongs in Services

All application business rules must live inside the appropriate Service.

Example:

```text
TicketService
```

may determine whether:

* A ticket can be reopened
* A ticket can transition to another status
* An agent can be assigned
* An SLA should be recalculated
* A notification should be created

---

### Rule 4 — Database Access Belongs in Repositories

Services must call repositories when application data must be retrieved or persisted.

Do not write database queries directly inside:

* Controllers
* Request classes
* Services

---

### Rule 5 — Maintain Separation of Concerns

Do not duplicate responsibilities between architectural layers.

Use:

```text
Request = Validation and incoming request processing

Service = Business logic

Repository = Database access
```

---

# Database

The project uses:

```text
MySQL
```

Use the existing backend framework's recommended MySQL database library, ORM, or query builder.

Do not introduce an additional ORM unless required.

---

## Database Configuration

Database credentials must be loaded from environment variables.

Example:

```env
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=ticketing_system
DB_USERNAME=
DB_PASSWORD=
```

Never hardcode database passwords, usernames, connection strings, API keys, or secrets in the source code.

Do not commit `.env` files containing real credentials.

Provide or maintain an `.env.example` file containing placeholders where appropriate.

---

# Database Schema

Use migrations or the backend framework's equivalent schema management system whenever supported.

Do not manually depend on undocumented database changes.

Database tables should use:

* Primary keys
* Foreign keys where appropriate
* Indexes for frequently searched fields
* Created timestamps
* Updated timestamps where appropriate

Consider indexes for fields commonly used by the ticketing application, including:

```text
ticket_number
customer_id
assigned_agent_id
department_id
category_id
status
priority
created_at
```

---

# API

The frontend must communicate with the backend through API endpoints.

Avoid embedding backend/database functionality directly into the React application.

Typical flow:

```text
React
   ↓
HTTP/API Request
   ↓
Backend Route
   ↓
Controller
   ↓
Request Validation
   ↓
Service
   ↓
Repository
   ↓
MySQL
```

Use consistent JSON responses.

Example success response:

```json
{
  "success": true,
  "message": "Ticket created successfully.",
  "data": {}
}
```

Example error response:

```json
{
  "success": false,
  "message": "Validation failed.",
  "errors": {}
}
```

---

# Error Handling

Errors must be handled consistently.

The backend should distinguish between:

* Validation errors
* Authentication errors
* Authorization errors
* Resource not found errors
* Business-rule errors
* Server errors

Do not expose:

* Stack traces
* Database passwords
* SQL queries containing sensitive information
* Internal server paths
* Application secrets

to end users.

---

# Frontend API Handling

React components should not duplicate API logic unnecessarily.

Where appropriate, organize reusable API communication separately from UI components.

Example:

```text
frontend/
└── src/
    ├── components/
    ├── pages/
    ├── services/
    ├── hooks/
    ├── utils/
    └── assets/
```

Suggested frontend services:

```text
authService
ticketService
userService
departmentService
categoryService
reportService
```

These frontend services are API clients and are separate from the backend `Services` business-logic layer.

---

# Authentication and Authorization

The application must implement secure authentication.

Authorization must be enforced by the backend and must not rely only on hiding frontend buttons.

Primary roles:

```text
Customer
Staff / Agent
Manager
Administrator
```

Every protected API endpoint must verify the authenticated user's permission to perform the requested operation.

---

# Ticketing System Development Rules

When implementing ticket functionality, maintain the following supported statuses:

```text
New
Open
Assigned
In Progress
Waiting for Customer
Resolved
Closed
Cancelled
```

Supported priorities:

```text
Low
Medium
High
Critical / Urgent
```

Default SLA:

| Priority          | First Response | Target Resolution |
| ----------------- | -------------: | ----------------: |
| Critical / Urgent |     30 minutes |           4 hours |
| High              |         1 hour |           8 hours |
| Medium            |        4 hours |          24 hours |
| Low               |        8 hours |          48 hours |

SLA values must be configurable instead of being permanently hardcoded throughout the application.

---

# Notifications

Initial notification channels:

```text
Web Application
Email
```

Design notification functionality so additional channels can be added later without requiring major restructuring.

Do not implement SMS, WhatsApp, Messenger, Telegram, or other third-party notification integrations unless explicitly requested.

---

# Development Quality

When implementing changes:

1. Inspect existing code before modifying it.
2. Follow the existing project's coding conventions.
3. Avoid duplicating existing functionality.
4. Keep functions and classes focused on one responsibility.
5. Use descriptive variable, function, class, and file names.
6. Do not hardcode configuration that belongs in environment variables or settings.
7. Handle errors properly.
8. Validate all externally supplied input.
9. Enforce authorization on the backend.
10. Run available tests, builds, linters, and type checks after changes.

---

# Do Not

Do not:

* Put SQL/database operations in controllers.
* Put SQL/database operations in Request classes.
* Put raw database queries in Services.
* Put business logic in repositories.
* Put major business logic in controllers.
* Trust frontend validation alone.
* Hardcode database credentials.
* Expose secrets to the React frontend.
* Change the backend framework without permission.
* Install unnecessary dependencies.
* Rewrite working code unnecessarily.
* Delete existing functionality unless explicitly requested.

---

# Required Workflow When Given a Development Task

For every substantial task:

1. Inspect the relevant existing files.
2. Understand the existing architecture.
3. Identify the required Request class.
4. Identify the required Service.
5. Identify the required Repository.
6. Identify any required database migration/model changes.
7. Implement the backend following:

```text
Request → Service → Repository → MySQL
```

8. Implement or update the React frontend.
9. Connect the frontend to the backend API.
10. Handle loading, success, validation, and failure states.
11. Use SweetAlert2 where appropriate.
12. Run relevant tests.
13. Run the frontend production build.
14. Check for errors.
15. Summarize the files changed and tests performed.

Do not declare the task complete if the build or relevant tests are failing unless the failure is unrelated and clearly reported.
